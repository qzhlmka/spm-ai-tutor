# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"study-assistant" — a Fastify + TypeScript backend (API-only) for a RAG-based SPM tutor covering multiple subjects (Add Maths, Physics, Sejarah/History, and others), plus a separate React frontend in `frontend/`. Textbook and past-year-question PDFs are ingested into a Supabase/Postgres vector store; a chat endpoint retrieves relevant chunks across the whole knowledge base and answers student questions, using the tutor's own knowledge grounded in the Malaysian KSSM/SPM curriculum plus that retrieved context. The tutor is scoped to SPM/KSSM schoolwork only — off-topic requests, jailbreaks, and persona-override attempts are declined by the system prompt in `src/lib/chat-handler.ts`.

The `frontend/` directory (Vite + React + TypeScript + Tailwind, its own `package.json`) is the only supported UI — a Claude.ai-style chat interface with KaTeX math rendering, per-user conversation history, and Supabase Auth login. The backend is a pure JSON API; it serves no HTML.

## Commands

**Local development — one command, one port:** `cd frontend && npm run dev`. This serves the whole app on `http://localhost:5173` — UI, `/api/chat`, `/api/conversations`, and `/health` — via a Vite plugin (`frontend/vite-plugins/api.ts`) that runs the backend logic directly inside Vite's own dev server process. No separate backend process needed for day-to-day dev.

Frontend (run from `frontend/`):
```bash
npm run dev          # Vite dev server on :5173 — serves the UI AND the API routes (see Architecture below)
npm run build        # Production build (tsc -b && vite build)
npm run lint         # oxlint
```

Backend (run from the project root) — a standalone Fastify server, used for production deployment (where Vite's dev server doesn't exist) or when you specifically want the API running on its own port/process:
```bash
npm run dev          # Dev server with watch (tsx watch src/server.ts), listens on PORT (see .env)
npm run build        # Compile TypeScript to dist/
npm run start        # Run compiled server (node dist/server.js)
npm run typecheck    # tsc --noEmit
npm run ingest -- <file.pdf> --exam-board SPM --subject 'Add Maths' --topic Differentiation [--dry-run] [--vision] [--topics-from-db] [--questions-only] [--start-page N] [--end-page N]
npm run reembed      # Re-embed all content_chunks after switching embedding models (see sql/migrate_e5_base*.sql)
```

There is no backend test suite configured yet.

Required env vars (see `.env.example`): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `PORT`. Validated at startup via `src/lib/env.ts` (zod schema) — the process throws immediately if any are missing/invalid. `frontend/package.json`'s `dev`/`preview` scripts load the root `.env` explicitly (`node --env-file=../.env ...`) since Vite's cwd is `frontend/`, not the project root.

**Known env-var gotcha:** a stale `OPENAI_API_KEY` can linger in an already-open shell session even after being changed/removed in `.env` or `~/.zshrc` — if the app appears to hang or 401 on OpenAI calls, `unset OPENAI_API_KEY` before restarting the dev server so it picks up the current value from `.env`.

## Architecture

### Chat request flow

The chat logic lives once, in `src/lib/chat-handler.ts` (`handleChatRequest()`), and is called from **two independent entry points** so it never exists as two drifting copies:

1. **Standalone Fastify backend** (`src/server.ts` → `src/routes/chat.ts`, `src/routes/conversations.ts`, `src/routes/materials.ts`, `src/routes/health.ts`) — the production-shaped entry point. Each route is a thin wrapper: call `requireUser()` (below), then the relevant `src/lib/*` function, then map the result's `{ status, body }` onto a Fastify reply.
2. **Vite dev-server plugin** (`frontend/vite-plugins/api.ts`) — for local dev only. Hooks into Vite's own `configureServer`/`configurePreviewServer` and adds the same API routes as middleware directly on Vite's Node process, calling the exact same `src/lib` functions. This only runs in Node (never bundled into the client-shipped React app), so backend secrets stay server-side. This plugin doesn't exist in a real production deployment, so production still needs the standalone Fastify backend above, deployed as its own process.

`handleChatRequest()` takes `{ question, attachments?, conversationId? }` plus an `AuthedUser | null`. It runs retrieval as **four parallel lanes, merged and deduped into a 12-chunk context block** (`MAX_CONTEXT_CHUNKS`). Two lanes hit `match_content_chunks` (a pure whole-knowledge-base cosine search, no subject/topic pre-filter) for 5 chunks each — once with the bare question, once with the question prefixed with the prior turn (to resolve pronoun-heavy follow-ups like "sketch it"). A third hits `match_teacher_materials` — the same cosine search restricted to `material_id IS NOT NULL` rows, because a few dozen teacher chunks otherwise lose the whole-KB search to thousands of textbook chunks on the same topic. That lane uses the **bare question only**, deliberately: running it on the prior-turn-prefixed query too was tried and reverted, because a 300-char prior turn dominates the embedding and turns the lane into "find chunks like my last reply" — every teacher chunk then cleared the cutoff on every unrelated follow-up. See the comment beside that RPC call for the measurements showing why no cutoff can fix it. The fourth lane is `match_teacher_materials_lexical` — IDF-weighted keyword search over teacher chunks, covering what dense vectors structurally cannot see, namely a student quoting their teacher's own wording (a mnemonic, shorthand, or teacher-specific term). Teacher-vector hits lead the block (up to 6, gated on `TEACHER_MATERIAL_MIN_SIMILARITY`), then up to 2 lexical-only hits (gated on `TEACHER_MATERIAL_MIN_LEXICAL_RANK`), then textbook chunks fill the rest.

**Only chunks that passed a teacher lane's gate are labelled as the student's own teacher's material** (`gatedTeacherChunkIds`), never every chunk with a `material_id`. A teacher chunk can also arrive via the whole-KB lanes without clearing any relevance gate — and it routinely does mid-conversation, since those lanes run the prior-turn query. Labelling those invokes the prompt's "treat as completely authoritative / TEACH FROM IT" rules on a chunk nothing established was relevant, which made the tutor volunteer the teacher's notes in unrelated answers. Ungated teacher chunks stay in the context as ordinary background knowledge. All the cutoffs in this path are empirically tuned against the real KB, with the probe results and the failed alternatives recorded in the comments beside each constant — re-measure rather than adjust them by feel. `TEACHER_MATERIAL_MIN_SIMILARITY` is now 0.75 and is only a **recall net**, not the relevance decision: chunks clearing it go to `judgeTeacherMaterialRelevance()`, a forced-tool-call request on `TUTOR_MODEL` that decides which are genuinely on-topic. A single similarity number was proven unfixable — positives measured as low as 0.7440 (a student quoting the teacher's own mnemonic) while same-subject negatives reached 0.8686, so the distributions overlap across their whole range; the previous 0.81, then 0.83, cutoffs each traded false positives against discarding correct hits (0.83 discarded 3 of 5 known-good hits in a recall probe). The gate fails **closed** — on any error it falls back to the old 0.83 cutoff, since an ungated wide net is the exact false-positive mode it exists to prevent. It must use a forced tool call, not "reply with JSON": measured on Haiku 4.5, the model wrapped JSON in a ```json fence *and* appended commentary, which no fence-stripping parsed reliably — a tool schema is the only structured-output guarantee that does not depend on the model behaving. **The tutor is strictly grounded: it teaches only from retrieved chunks and the student's attachments, never from its own training.** `TUTOR_SYSTEM_PROMPT`'s opening `GROUNDING` block overrides every other rule in the prompt, and reverses the earlier design in which the model answered from its own knowledge and treated retrieval as mere supporting context. The reason is legibility, not accuracy — an ungrounded answer is often correct, but a student cannot tell which half of a reply came from their teacher's material and which the model recalled, and that uncertainty is what the product exists to remove. The distinction the block draws is **facts vs. reasoning**: asserting a formula, date, definition or marking convention that isn't in the retrieved material is forbidden, while *applying* a retrieved method to the student's own numbers — substituting, doing the arithmetic, checking their answer — is required. Collapsing that distinction breaks the main use case, since a student's specific homework question is never itself in the knowledge base. When retrieval returns nothing relevant, the tutor says so and stops rather than assembling a partial answer around the gap.

Three consequences are load-bearing. (1) The prompt's own content is grounded by definition — otherwise the model refuses to use the `SUBJECT SCOPE` block, which hard-codes the Mathematics-vs-Additional-Mathematics topic split so it stops guessing at Malaysia-specific curriculum trivia. (2) App meta-questions ("how do I use this") are exempt; they aren't subject matter. (3) The tutor must **never recite a list of subjects it covers** — it can't see the catalogue, only the chunks retrieved for the current message, and a probe found it advertising Biology (zero chunks) in the same session it refused a Biology question. The knowledge base currently covers only Chemistry, Physics, Mathematics, Add Maths and Sejarah, so strict grounding means every other SPM subject is declined outright. The one place it MAY list them is a `catalogue` turn (below), where the list comes from the database rather than from the chunks it happened to retrieve. Widening coverage is now a content problem, not a prompt one.

Correcting bad teacher material is narrowed by the same rule: `WHEN THE MATERIAL HAS A GAP OR AN ERROR` lets the tutor name what looks wrong, say it contradicts other retrieved material, or say it cannot verify — but not supply the corrected fact from memory. Where other grounded material has the right version it uses that; otherwise it stops at naming the doubt and points at the teacher. A diagram (function graph / triangle / vector) is generated server-side via a second, tool-calling request (`src/lib/visual.ts`) only when the student explicitly asks for one. Image/PDF attachments (`src/lib/attachments.ts`) route the turn through `VISION_MODEL` instead of `TUTOR_MODEL`. The API still returns `sources` in the response, but the UI no longer shows them anywhere (2026-10-19): the Files panel replaced both the Sources panel and the per-answer "Sources (n)" toggle, so a student sees only files they can open. **A chat turn lists the teacher's PDFs for download** — the **Files panel** beside the chat at `xl` (`FilesPanel.tsx`), and on narrower screens a drawer behind the top bar's Files button, from the `materials` field on the chat response. Until 2026-10-19 these were cards under the answer. The cards reversed an earlier removal of a per-turn download chip, and both reasons that removal was right have since gone:

1. *The old chip fired on nearly every message.* Its gate was the teacher-material **lane**, which at the time ran the prior-turn-prefixed query — measured, all 12 teacher chunks cleared the cutoff for 10 of 10 unrelated questions after one chemistry turn, "thanks" included.
2. *It needed a precision-critical "is this document really this student's?" decision.* It no longer does — there is no class scoping, all material is one shared pool, and `getMaterialDownloadUrl()` checks only that the caller is logged in. A card asserts nothing the Materials tab doesn't already make true for everyone.

**The card is gated on `attachableChunkIds`, which is deliberately stricter than the `gatedTeacherChunkIds` used to label context.** Getting this wrong shipped the bug twice in one sitting, both times by reusing a gate that was tuned for context inclusion — where a stray chunk is harmless background the prompt already tells the model to ignore — as if it were a relevance gate for a visible claim. It is not. Attaching a file asserts "this is the material your answer came from", and that needs its own evidence:

- **Not `gatedTeacherChunkIds`.** `judgeTeacherMaterialRelevance()` is shown the tutor's previous reply, which it needs for genuine follow-ups ("what's the mnemonic?"). But that lets the *previous reply* pick the file when the question carries no topic of its own. Reproduced: after a turn on anode half-equations, "check what is this" (a student photographing something) scored every teacher chunk 0.79–0.81, cleared the 0.75 recall floor on all of them, and the judge correctly called redox notes relevant to a redox conversation. The answer was right — "this is a DuitNow bank receipt" — with a Redox Equilibrium PDF stapled underneath. The judge now returns **two** lists: `relevant_ids` (unchanged, drives context labelling) and `question_relevant_ids`, the subset that stands up with the previous reply removed. The second is enforced as a subset in code, not trusted from the model.
- **Not the lexical lane either.** Exempting it looked safe — it matches the student's literal words in the bare question, so it is question-driven by construction. Wrong: `rank` is a sum of per-term IDF, not a topical judgment. Measured, "explain that again" put a Chemical Consumer chunk ("Explain how cleansing action of soap…") top of the lane at rank 10.06 on 2 matched terms, and "teach me about rate of reaction" pulled a Thermochemistry chunk at 7.363 — both well clear of the 5.0 floor. Lexical-only hits are excluded from attachment entirely. The cost is that a student quoting their teacher's mnemonic gets the teaching without the file, which is the right trade: the wording is what they needed.
- **A similarity floor cannot substitute for any of this** — the overlap measurements beside `TEACHER_MATERIAL_MIN_SIMILARITY` rule it out, and "check what is this" at 0.8080 outscores genuine positives measured as low as 0.7440.

**A subject mismatch is removed in code, before the judge sees it.** When the bare question names exactly one subject (`subjectsNamedIn()` in `exam-label.ts`), teacher chunks from any other subject are dropped from both teacher lanes. Reported: *"past years topic on consumer mathematics"* came back with a Chemistry PDF attached. All 108 teacher uploads are Chemistry, e5's compressed similarity band scores them all ~0.79–0.80 against a maths question (clearing the 0.75 recall floor), and the judge approved *"Bab 5: Kimia Konsumer (Chemical Consumer)"* on the one shared word "consumer". Which topic is relevant is a judgment an LLM can reasonably get wrong. "This chunk is Chemistry and the student said Mathematics" is a fact, and a fact should not be delegated to a model. The guard is **question-only**: inferring the subject from history, as the exam lane does, would let a stale subject *subtract* the student's notes when the conversation moves on without naming the new one, and losing class notes is the costly direction. It stands down when a question names no subject or several ("how is maths used in chemistry"), and it excludes the alias "history", which is an ordinary English word ("explain the history of the periodic table" is a Chemistry question). Those cases go to the judge, whose excerpts are now labelled with their subject as a backstop. Measured: 0/11 parser errors, and the reported conversation goes from 12 Chemistry candidates to 0, while genuine Chemistry questions still attach their notes.

The judge fails closed differently for each list: `relevant` falls back to the old 0.83 similarity cutoff (losing it costs a student their class notes), `questionRelevant` falls back to **empty** (losing it costs a convenience; getting it wrong puts a stranger's chapter under the answer).

**Which files are listed (2026-10-19).** Two sources, decided in `resolveMaterialsStage()`. (1) On every turn, the files the answer was taught from (`attachableChunkIds`, the judge's question-only verdict, capped at `MAX_ATTACHED_MATERIALS` = 3). This used to need an explicit request or a "yes" to an offer, because a card under the reply reads as the tutor handing over a document nobody asked for; a side panel listing what an answer drew on is a reference, so the offer note, `resolveOfferedMaterials()` and the confirm branch were removed. Measured: "what is a standard solution" lists 1 file, "how to calculate heat of neutralisation" 3, Physics and Maths questions 0. (2) When the student asks for files, the request is answered from the file list itself by `detectFileRequest()` (`material-lookup.ts`, forced tool call `report_requested_files`, Langfuse generation `material-topic`). **Whether they asked is decided by the model from the message and the last 6 messages, never by keywords**: a phrase list was the gate first and missed "can you retrieve me the latest materials on this topic", and widening it only moves the miss to the next wording. It runs on every turn except a bare greeting, in the `route` node beside the router and the standalone rewrite (about 1.6–2.2 s, so it overlaps them; about $0.002 a turn), and a file request is never conversational, so one the router files as `catalogue` still reaches the file step. It then picks topics from the library's own topic list (or a whole subject for "all the chemistry notes") and lists **every** downloadable file of them. Measured 12/12 on two runs: positives with no file keyword at all ("where can i study this from" mid-conversation → 23 Acid, Base and Salt files; "ada tak benda yang cikgu bagi pasal redoks" → 7 Redox), and negatives "explain neutralisation", "give me a past year question on acid base", "what is a composite material", "my answer is pH 7, is that right?", "yes" after an offer of another question. Passage similarity was the wrong tool for "give me the file": measured on the same requests, it returned a combined-class note for "nak nota kimia konsumer" and missed "Nota Kimia Konsumer.pdf", showed 3 of 12 Thermochemistry files, and answered "chapter 5" with a Chapter 4 file. A chapter number alone matches nothing and lists nothing — the prompt note then tells the tutor to ask which topic (chapter numbers differ between Form 4 and Form 5) — rather than falling back to a guess. A subject with no uploads (every upload is Chemistry as of 2026-10-20) is reported as `missingSubject` from the tool's `subject` field, inferred from the conversation when unnamed: asking "which topic?" there had no good answer, so the tutor now says no teacher has uploaded files for that subject yet, then teaches the topic if one was named or asks which one if not (it presented an unrequested past-year question until told not to). Measured 12/12 on two runs, including "where can i study this from" mid-transformer-conversation → Physics. Only a failed lookup call falls back to the passage-matched files. **"Do you have" about the syllabus is not a file request (2026-10-26).** "Which Form 2 maths chapters do you have?" was intermittently read as asking for files, so the tutor answered "No teacher has uploaded any Mathematics files" instead of listing the chapters (found by golden-v5). The tool description now says that asking what the tutor holds (chapters, topics, forms, counts) is false. Measured 24/24 over 12 phrasings × 2, including the file requests above, and "ada nota maths tak" still gets the no-uploads reply. A code backstop ("let catalogue win when no topic is named") was rejected: the failing case named a subject, so the backstop would not have caught it, and it would have silenced a real "ada nota maths tak". The router still sends a bare "yes" to `schoolwork`, since it usually answers a tutor's question.

`resolveAttachedMaterials()` additionally requires `status = 'done'` and a non-null `file_path` — the same pair `listMaterialsLibrary()` filters on, so a file is only listed if it can actually be signed (the lookup uses the same filter). A storage-failed upload still has live chunks the tutor teaches from; it just has no file to hand over, and a link that 404s is worse than none. The signed URL is minted **on click**, not embedded at render time: it expires in 5 minutes and a message stays on screen far longer. The list is not persisted with the message, so a reloaded conversation shows an empty panel until the next answer — same as `sources`. Within an open conversation the panel accumulates across answers.

The Materials tab (`MaterialsLibrary.tsx` → `listMaterialsLibrary` / `getMaterialDownloadUrl`) remains the place to *browse everything*; the Files panel is only this conversation's files, with a "Browse all materials" link. Retrieval feeds the material's content to the tutor either way.

`TUTOR_SYSTEM_PROMPT` is kept truthful rather than told a blanket rule: `resolveAttachedMaterials()` runs **before** the model call and the resulting filenames go into the prompt as a "Files in the Files panel beside your reply" list (counts per topic past `MAX_NAMED_FILES` = 12, since a whole-subject listing is 108 files). The model may refer to a file only when that list is present, must never promise to attach one itself (what appears is decided before it replies), and is told the file is never a substitute for teaching. Without the list it falls back to pointing at the Materials tab.

Conversation history (`src/lib/conversations.ts`) is persisted per-user in Postgres (`conversations`/`messages` tables) and fed back as context up to `HISTORY_MESSAGE_LIMIT` (20) prior turns.

**Auth & roles:** `src/lib/auth.ts`'s `requireUser()` verifies a Supabase Auth session token (`Authorization: Bearer <token>`) via `supabase.auth.getUser()`, then idempotently upserts a matching `public.users` row (that row's id IS the auth user id, and what `conversations.user_id`/`messages` key off) and returns its `role` (`'student' | 'teacher'`, defaulted to `'student'`). The upsert never writes `role` itself — it's only ever flipped by a manual DB update — so a returning student can't accidentally reset an account that's been promoted to `'teacher'`. `role` gates the material-upload endpoints (below) and the student daily usage cap. Supabase writes throughout the backend use the `service_role` key (`src/lib/supabase.ts`), not the anon key — RLS with no policies defined will silently block inserts/reads via the anon key.

### Teacher materials, profile, and usage caps

`src/lib/materials.ts` lets a `'teacher'`-role user upload their own PDF (base64 body, `POST /api/materials`) and have it ingested through the **exact same** `extractPagesFromBuffer` → `runIngestion` pipeline the CLI uses (see below) — one implementation shared by both entry points, tagging inserted `content_chunks` rows with `material_id`. It **always** runs the vision-OCR path (`extractPagesVision`), never the plain text layer: teacher decks routinely mix real caption text with diagrams embedded as images, which sails past `looksLikeScannedText()` while the diagrams themselves are silently dropped. Decks are small (20-40 pages), so the OCR cost is worth paying unconditionally here — unlike the CLI's textbook-scale ingestion, where the heuristic still applies. This requires `pdftoppm` (poppler) to exist in the deploy environment; see `nixpacks.toml`, without which every upload fails with `spawn pdftoppm ENOENT`. Uploads are deduped on a sha256 `content_hash` of the file bytes, so a byte-identical re-upload is rejected rather than creating a second competing set of chunks. The original file is also stored (private `materials` storage bucket) so students can download it later via a signed URL (`getMaterialDownloadUrl`, 5-minute expiry) — `listMaterialsLibrary()` is the student-facing "browse what's been uploaded" list; `listMaterials()` is the teacher's own upload-history view. Teachers can also rename (`PATCH /api/materials/:id`, which propagates corrected `subject`/`topic` down to the material's `content_chunks`) and delete (`DELETE /api/materials/:id`, which removes the chunks **before** the row — `content_chunks.material_id` is `on delete set null`, so dropping the row first would orphan chunks the tutor keeps teaching from). Delete is exposed in both the library and the upload-history view, because the library filters to `status = 'done' AND file_path IS NOT NULL` and so cannot reach a storage-failed upload that still has live chunks.

**Adding a link lives in the upload panel, not its own screen.** `MaterialUpload.tsx` opens on a Material/Link choice and asks a link for the same describing fields a PDF gets — name, subject, topic — because from a student's side they serve the same purpose, and a teacher shouldn't have to know which of the two kinds they want before picking a screen. Topic stays optional for a link only (the column is nullable by design: a general revision channel has no single topic, and forcing one produces junk topics that fragment the grouping). The form says plainly that the tutor can point at a link but never reads the page, since that is the one real difference between the two tabs. `ResourceLinks.tsx` keeps browsing plus edit/delete and lost its own add form — the same split the materials library already uses, where delete is reachable both where you manage and where you browse. Consolidating surfaced a bug that had been there since the feature shipped: `createResourceSchema.topic` was `.optional()` but not `.nullable()`, while `ResourceInput` on the client declares `topic?: string | null` and any form with a blank optional field sends null — so every link saved without a topic failed with a 400 that named no field. Create now matches update, which was already explicitly nullable.

`src/lib/usage.ts` enforces `STUDENT_DAILY_BUDGET_USD` — checked via `checkUsageLimit()` before any model call in `handleChatRequest()`, blocking students (never teachers) once `usage_daily.cost_usd` for the day hits the cap. **The cap is off unless the `STUDENT_DAILY_BUDGET_USD` env var is set** (turned off 2026-10-16; it was a fixed $0.20/day). Spend is still recorded on every turn either way, so setting the variable (e.g. `0.2`) turns it back on with no deploy of code; the profile's usage bar is hidden while it is off. The pricing rules below still apply — they matter again the moment the cap is back. `recordUsage()` computes real cost from each Anthropic response's token usage against `PRICING_PER_1M_TOKENS`. `src/lib/profile.ts` (`GET /api/profile`) is how the frontend learns the logged-in user's `role` and today's usage — `AuthedUser` itself intentionally carries only `id`/`email`/`role` so the auth check on every request stays cheap.

### Ingestion pipeline (`src/ingest/`)

`src/ingest/ingest.ts` (run via `npm run ingest`) is the main one-shot pipeline: extract PDF text per-page → batch pages (6 at a time, `PAGES_PER_BATCH`) → send each batch to `CHUNKING_MODEL` with the prompt in `src/ingest/chunking-prompt.ts` to split into typed chunks → embed each chunk → insert into `content_chunks`. The chunk→embed→insert core is `runIngestion()`, exported and reused as-is by the teacher upload path (`src/lib/materials.ts`) — one implementation, not two drifting copies; the CLI's `main()` just handles arg parsing, extraction-method choice, and `--dry-run` branching around it. **Inserts happen batch by batch, not all-or-nothing** — each 6-page batch is chunked, embedded and inserted before the next is chunked, so a mid-run failure leaves the batches before it in the DB. Re-running the whole file on top of that duplicates every chunk already inserted (retrieval dedupes by row id, not content, so duplicates take extra context slots). Either delete `where source_file = X` first, or resume with `--start-page` at the first missing page: the batches completed so far are visible as distinct `created_at` seconds per `source_file`, and the highest page number in their `source_page_images` confirms where it stopped. `chunkBatch()` retries invalid JSON up to 3 times, and `chunkPages()` splits a batch in half when the model's output hits its length limit — measured on Chemistry Form 5 KSSM pages 31–36, which truncated on every attempt (splitting can separate a question from a solution across the cut, so it is the fallback, not the default). Supports `--dry-run`, which writes chunks to `<basename>_chunks_review.json` instead of inserting, for manual review before committing to the DB.

Text extraction branches on the `--vision` flag:
- Default: `extractPages()`/`extractPagesFromBuffer()` via `pdf-parse` — fast, but requires a clean embedded text layer.
- `--vision`: `extractPagesVision()` (`src/ingest/vision-extract.ts`) — renders each page via `pdftoppm` and transcribes it with a vision model, for PDFs with a garbled or absent text layer (scanned textbooks). Caches the full document's OCR results keyed by source PDF path (not by page range), so multiple `ingest.ts` invocations against different page slices of the same file only pay the OCR cost once; checkpointed/resumable via a `.partial` file. `looksLikeScannedText()` is a heuristic (>30% near-empty pages, or <200 avg chars/page) kept for the CLI path. The teacher-upload path no longer consults it — it always runs vision (see above).

Chunking rules (enforced by the LLM prompt, not code) are strict: worked examples and formulas are never split from their explanation/solution; bare exercises without solutions are dropped; page headers/footers/branding are filtered out. **A question's solution is frequently on a LATER page than the question**, which is the normal shape of annotated class notes — a printed exam question followed by handwritten working — so the prompt requires scanning the whole batch (matching on a repeated question label like "Soalan 5 : trial Pahang") and emitting question+solution as one chunk. Without that rule the anti-fabrication guard below misfired badly: measured on two real note files it discarded 9 of 24 chunks, including fully-worked trial questions whose answers were present one page over. The prompt also states explicitly that informal handwritten shorthand counts as a real solution, since the chunker otherwise treats only typeset working as authoritative. The chunker is also explicitly forbidden from **deriving an answer from its own knowledge** to fill a gap in the source, and tags every chunk with `answer_status`; `past_year_question` chunks marked `not_in_source` are dropped before embedding. This exists because fabricated and hedged MCQ answers ("Jawapan: Semua padanan adalah betul") were reaching students labelled as authoritative teacher material — a real re-ingestion of 5 teacher decks dropped 12 such chunks. Each chunk is tagged with `content_type` (`concept` | `worked_example` | `past_year_question` | `formula` | `common_mistake`), `difficulty`, `subtopic`, and `source_note`.

Before embedding, every chunk's text is run through `passageTextForChunk()` (`src/lib/chunk-embedding-text.ts`), which prepends a descriptive prefix for two chunk kinds that otherwise embed poorly: `past_year_question` chunks (raw exam text carries no signal that it *is* a past-year question) and teacher-uploaded material chunks (often Malay-language, low-volume, and get swamped in whole-knowledge-base cosine search without an English subject/topic anchor). Plain concept/formula/worked-example chunks are left as-is since the student's question already overlaps them semantically.

Past-year-question ingestion has subject-specific scripts (`src/ingest/ingest-past-year.ts`, `src/ingest/ingest-physics-past-year.ts`) with their own OCR helpers (`past-year-ocr.ts`, `physics-past-year-ocr.ts`), since matching questions to answer keys (Skema) is subject-specific and PDF page order isn't reliably sequential in some source scans — sample/verify actual page order before assuming a layout when adding a new subject's past-year pipeline.

**Answer-scheme PDFs come in two shapes, and which one you have decides the whole approach — render a page and look before writing anything.** (a) *Answers marked on the question itself*, by highlighting the correct option (the Sejarah SKEMA SELEKOH files). `pdftotext` discards highlight colour entirely, so these MUST go through `--vision`, and `vision-extract.ts`'s transcription prompt carries an explicit rule to record markings inline (`C. Siantan [HIGHLIGHTED]`); without it the vision model also drops them and every question reads as answerless. `chunking-prompt.ts` rule 3 then treats that marker as the answer key. (b) *Answers in a separate file* (Mathematics: `MATEMATIK BUKU SELEKOH` holds the questions, `KERTAS 1 F4/F5` hold bare answer grids). Neither half is usable alone — ingesting the key by itself yields chunks reading "Soalan 1: Jawapan: C" with no question attached. `src/scripts/ingest-maths-past-year.ts` pairs them on `(form, chapter, printed question number)`, with `src/scripts/parse-answer-key.ts` reading the grids via pdftotext (clean typeset text; vision is *worse* at isolated single letters).

**The answer lookup is done in code, never by the chunking model.** Handing the model the key and asking it to match was tried and produced confidently wrong answers at scale: it renumbered questions from 1 within each 6-page batch and read off the key entry for that position, so book question 6 was stored with question 1's answer — 338 chunks, all plausible-looking, all wrong. The model now only transcribes the printed `question_number`; `runIngestion()` attaches the answer from its `answerKey` map afterwards. Verify any new pairing run the same way it was verified here: re-parse the key independently and assert every stored answer against it (394/398 matched, 0 contradictions).

**Pairing a question bank to a separate answer key is only valid when the question file IS the numbered module the key was written for.** Attempting it for the Chemistry class notes failed badly and was reverted: those notes bundle printed MODUL SELEKOH pages (whose numbering does match `chemistry/SKEMA SELEKOH/`) together with the teacher's own worksheets on the same chapter (whose numbering is independent). Keying on `(topic, question number)` matched both, so worksheet question 4 — "which element is in Group 18?", answer Neon — was stored with the module's answer A. Two further traps surfaced there and are worth knowing before trying again: two schemes both cover "Acid, Base and Salt" (`BAB 6 ASID BES` and `BAB 6 GARAM`) with independent numbering, so that topic can never be keyed by topic alone; and some grids list the same question number twice with different letters (`parse-chem-skema.ts` drops those rather than picking one).

**Number-based pairing was attempted twice for the Chemistry notes and failed twice; do not try a third variation without a fundamentally different key.** `src/scripts/repair-notes-answers.ts` and `validate-key-alignment.ts` are kept as the record of it. The second attempt added a semantic gate — sample a file's MCQs, ask a model whether the key's proposed answer is actually correct, reject below 70% agreement — and that gate calibrated cleanly (printed module 80%, teacher worksheet 20%, workbook 40%, against 25% chance). It still shipped wrong data, because it could not see the real problem: the modules number their MCQs 1..N *and* their structured questions 1..N, so a 5-mark "compare and contrast vulcanised rubber" got `Jawapan: A` from the MCQ grid. The gate samples via `extractMcqs()`, which requires an A–D option block, so subjective questions never entered the sample it scored. An independent audit of what was actually written — sampling stored chunks rather than the gate's own subset — found 77% correct among determinable questions and letters attached to essay questions. Both attempts were reverted with `--no-key`.

The lesson generalises: **a validation gate that samples a different population from the one being written is not a check on the write.** Audit the rows that landed, not the candidates that were considered.

**Verifying an injected answer against the key it was injected from proves nothing** — it is circular, and it is the reason the Chemistry breakage survived a check that the Mathematics breakage did not. That check only catches a *mechanical* fault (the chunker renumbering questions within a batch). Semantic alignment has to be tested independently: read a few questions and confirm the stored answer is actually correct, or match on the exam-source label each question carries (`TRIAL KELANTAN 2022 – (5)`), which both the module pages and the scheme's worked solutions print, and which — unlike a position number — cannot silently mean something else in a different file.

`--topics-from-db` makes each chunk pick its own `topic` from the subject's existing vocabulary, for whole-syllabus sources like a revision book that spans every chapter — a single `--topic` would otherwise stamp one wrong label onto every chunk, and that label is embedded into the passage text for `past_year_question` rows. The list is read with explicit pagination: PostgREST caps a response at `db-max-rows` (1000) and `.range()` cannot raise it, which silently returned 10 of Mathematics' 18 topics on the first run.

`--questions-only` is for a question bank printed **without** its answers, with no scheme available to pair (the Selekoh 2026 Chemistry F4/F5 modules, 2026-10-22). It reverses the drop rule for that file only: the chunker emits every exam question as a `past_year_question` with its printed label as `source_note`, and `runIngestion()` keeps the `not_in_source` ones, appending `QUESTIONS_ONLY_NOTE` ("No answer scheme in the source: work the question through with the student…") to the stored content, though not to the embedded text. The note is what keeps this safe: the tutor repeats any answer it finds in a chunk, so a question with no answer has to say so in its own text. This is the same reasoning that kept the 251 stripped-answer rows: an answerless question can still be taught, but one with a wrong answer can't. Rule 6 (never write an answer) is unchanged, but **the prompt alone did not hold**: on the full run, 6 of 469 questions still came back ending in "Jawapan: X". Two of those followed a highlight that vision OCR reported but the page does not have, and one was the wrong option (Kelantan 2025 Q22, stored as B; the working gives C). Under this flag, `stripAnswerLines()` therefore removes any answer line in code, and the 6 stored rows were repaired the same way. Prefer pairing with a real scheme on the printed exam label whenever one exists. **Non-question content under this flag is copied exactly as printed (2026-10-22).** On the Physics modules, which open each chapter with a bare formula box, the chunker followed rule 2 (a formula needs an explanation) and wrote its own: "These are fundamental formulas in the topic of heat…" on the real box, plus whole notes chunks that are on no page ("Subtopik ini membincangkan konsep arus elektrik…", "Konsep utama: …", and a "checklist" assembled from headings on later pages). An audit of every non-question chunk from the Selekoh 2026 modules, measuring how many of its 4-word runs appear in the OCR text, found 12 of 23 Physics chunks below 0.8, against 0 in Chemistry and Sejarah. The Add Maths cover pages scored 0.46–0.76 because the chunker added English translations of Malay headings. The questions-only rule now says rule 2 does not apply, and forbids summaries, overviews and assembled checklists; a dry run on the same pages then produced bare formulas only. **Audit by coverage against the source text, not by eye:** an authored sentence reads exactly like course notes. A run of 20+ repeated marks is also collapsed before chunking (`collapseMarkRuns`): OCR turned a dashed legend line into 7k characters, and the page failed with a length-limit error at every split.

Models: `gpt-4.1` for chunking and vision/OCR (`CHUNKING_MODEL`/`VISION_MODEL` in `src/lib/openai.ts`) — ingestion only. **Every live chat request goes to Anthropic's `claude-sonnet-5` (`TUTOR_MODEL` in `src/lib/anthropic.ts`)**: the tutoring answer (text and image/PDF attachments alike), the teacher-material relevance gate, and the visual-diagram tool-call decision (`ANTHROPIC_VISUAL_TOOLS`). The path was moved off `gpt-5.4` to `claude-haiku-4-5` first — matching content quality on real SPM questions, ~2x faster, ~40% of the per-token cost, and the deciding factor, correct compliance with `TUTOR_SYSTEM_PROMPT`'s scope rules where `gpt-5.4` answered an off-topic "write my essay" request — then to Sonnet 5 for answer quality. Sonnet 5 costs 2x Haiku 4.5 per token in both directions ($2/$10 per 1M vs $1/$5), so `STUDENT_DAILY_BUDGET_USD` buys roughly half as many turns; `PRICING_PER_1M_TOKENS` in `src/lib/usage.ts` is keyed by model string and must be updated in lockstep with `TUTOR_MODEL`, or `costUsd()` silently returns 0 and the cap stops enforcing.

**Sonnet 5 thinks by default when the `thinking` parameter is omitted** — Haiku 4.5 never did. All three call sites therefore pass `thinking: { type: "disabled" }` explicitly. This is not cosmetic: thinking tokens are billed against `max_tokens`, so on the two forced-tool-call requests (the relevance gate at 256 tokens, the visual decision at 1024) the model would spend the whole budget reasoning and return `stop_reason: "max_tokens"` with no `tool_use` block — the relevance gate would then fail closed to the old 0.83 cutoff on every single request, with no error anywhere. On the main answer (4096) it would truncate long worked solutions mid-sentence. To enable reasoning, raise that call's `max_tokens` first, then set `{ type: "adaptive" }` with a low or medium `output_config.effort`. Embeddings are **not** OpenAI or Anthropic — see below.

**Answer letters that point at nothing were stripped, not deleted** (`src/scripts/strip-unusable-answers.ts`, 251 rows: Mathematics 165, Physics 86). Two unrelated ingestion bugs left past-year chunks ending in a bare `Jawapan: C` on a question offering no lettered options — Mathematics because the MCQ-only KERTAS 1 key was paired onto Paper 2 structured questions by printed number alone, Physics because the options are laid out as diagrams/tables that OCR rendered as prose so the A–D block never reached the stored text. The detector requires **both** a bare letter line and fewer than two option labels: an answer spelled out in words (`Jawapan: A Ikatan ion`) works whether or not the options survived, which is why Chemistry and Sejarah were untouched at 0. The questions were kept because GROUNDING separates facts from reasoning — the tutor may not assert an official answer that isn't in the material, but it may work the question through with the student, so an answerless past-year question is still teachable while one carrying a wrong letter is not (the letter is the one thing the tutor is obliged to repeat). This deliberately overrides the ingestion-time rule that drops unanswered past-year questions; that rule governs what to ADMIT, and these rows were already admitted. New ingestions can't reproduce either bug: `looksLikeMcq()` in `ingest.ts` now blocks a key letter from attaching to a non-MCQ, and `ingest-physics-past-year.ts` applies the same check before appending its answer.

### Past-year questions by exam (`src/lib/exam-label.ts`)

A student can ask for a specific paper — "past year maths johor 2023", "soalan percubaan fizik perak 2022" — and get an exact answer, including an exact **no**. This is a filter lane, not a similarity lane, and that distinction is the whole feature: cosine search always returns *something*, so "Johor 2013" would otherwise hand over Selangor 2022 with no signal that it had substituted.

`content_chunks.exam_year / exam_authority / exam_district / exam_set / exam_question_no` (migration `add_exam_label_columns`) are parsed from the free-text `source` label by `parseExamLabel()`. Nothing upstream ever recorded the exam, and `source` is vision-OCR'd prose in five per-subject shapes, so the parser keys on the two things OCR gets right — a four-digit year and a place name from a closed list. It deliberately ignores the exam-type word, because that word is the one OCR destroys: "Percubaan" is stored six ways in Mathematics alone (`PERUBAHAN` 180, `PERCUBAAN` 177, `PERUBAAAN` 16, `PERUBCAAN` 7, `PERCAUBAN` 6, `PERUBAN` 6), and *Perubahan* is an ordinary Malay word meaning "change", so the commonest spelling is not a typo any speller would flag. Coverage: 2403/2487 authority, 2420/2487 year; the ~84 misses are rows whose label genuinely has no exam identity ("Question 25", "Achievement Test", the internal weekly quiz). `runIngestion()` sets these at insert time for every new past-year chunk (it didn't until 2026-10-08, which left 335 Chemistry rows unlabelled and made the tutor deny holding Negeri Sembilan 2022 — fixed by re-running the backfill). Backfill older rows with `src/scripts/backfill-exam-labels.ts` — idempotent, and safe to re-run after a parser change because **the exam label is not part of the embedded passage text**, so nothing needs re-embedding. Embedding it was considered and rejected: a cosine match on "Johor 2023" is a similarity, not a predicate, and cannot answer "none".

`match_past_year_by_exam()` filters on those columns and uses the embedding only to *order* what the where-clause already admitted, so it can return zero rows. `past_year_exam_coverage()` backs the "I have Johor 2021-2023, not 2013" reply — the prompt is told those are the only years it may claim, since a bare "no" is indistinguishable from a broken app.

**The query-side gate is the dangerous half.** `parseExamFilterFromQuestion()` requires an explicit past-year intent phrase *and* a year or place. The intent phrase is not optional: every Malaysian state name is also ordinary subject matter, and "terangkan sejarah Perak" would otherwise swap a history lesson for a list of Perak trial questions. The bare word "spm" is excluded for the same reason — students append it to everything. Measured on 16 phrasings: 7/7 intended, 0/9 false positives. Like the teacher lane and the file-attachment gate before it, it reads the **bare question only** — running it on the prior-turn-prefixed query would make every turn after a Johor question look like a request for Johor papers.

**A topic named with the paper goes first (2026-10-26).** The filter picks the paper, but similarity alone then picked the question: "soalan percubaan fizik Kedah 2025 tentang gelombang" got an Electricity question first, although Kedah 2025 has 3 on Waves. The lane now fetches up to `EXAM_LANE_POOL` (60) rows, finds the subject's topics the question names (`topicsNamedIn()` in `exam-label.ts`, on the question plus its `rewriteMalayTerms` English, against `subjectTopics()` from the catalogue cache), and puts those first before cutting to 10. If the whole filtered set came back and none is on the named topic, `examTopicMissing` tells the tutor to say the paper has none before offering another topic. The topic only orders the questions, never filters which papers match. Measured on the 11 past-year-request items in golden-v5: correctness 0.73→0.91 (Kedah waves 0→1). "asid bes dan garam" without the comma was added to the glossary, since only the comma form matched before.

What this does *not* do is return a whole paper. The sources are topic-organised revision compilations that cherry-pick single questions from dozens of trial papers (Johor 2023 Mathematics = 79 questions across 7 districts), so no complete paper was ever ingested. That is a content gap, not a retrieval one.

### Diagram-dependent past-year questions (`source_page_images`)

Reported: a past-year question depending on a diagram often can't be answered, even though retrieval found it. Measured directly against the real KB: 141/452 Add Maths past-year chunks, 123/454 Chemistry, 85/430 Physics and 39/398 Mathematics mention a diagram ("Rajah X menunjukkan...") with **no usable description captured at all** — the question asks about coordinates/values/labels that exist only in the source image. A second, uncounted failure mode sits beside that one: some chunks DO get a bracketed description from vision OCR, but for Cartesian-plane/transformation questions it's often vacuous — `[Graph showing two trapeziums, ABCD and EFGH, on a Cartesian plane]` restates the caption without reading off the actual plotted coordinates the question depends on.

**A text description is structurally lossy for this class of question**, so the fix stops trying to improve the description and instead keeps a pointer to the real rendered page image, handed to the (vision-capable) tutor model at answer time — the same mechanism already used for a student's own uploaded photo (`attachments.ts`), just sourced from the knowledge base instead of the current turn's upload. `content_chunks.source_page_images text[]` (`sql/migrate_add_exam_page_images.sql`) holds storage paths into the private `exam-page-images` bucket; all four retrieval RPCs return it (`sql/migrate_expose_source_page_images.sql`).

**Attribution is chunk-to-PAGE, not chunk-to-BATCH**, even though chunking only ever knows a 6-page batch (`PAGES_PER_BATCH`) at a time. `matchingPageIndices()` (`ingest.ts`) finds which page(s) within the batch a chunk's own `content` actually came from, by matching a shrinking word-window against each page's raw OCR text — and tries several word OFFSETS into that content, not just the start. This is load-bearing: a stored chunk routinely opens with a label the chunking model itself added ("Question:", "Marking Scheme:") that never appeared on the real page, so anchoring only at offset 0 built a needle out of that label and matched nothing on every single past-year chunk — verified directly against a real cached OCR document before shipping this. The next page is always included alongside a match, since the ingestion pipeline's own chunking rule allows a solution (or a diagram's continuation) to land on the page after the question. No match found (an unexpectedly paraphrased opening) means no image attached — the same fail-**empty**-not-wrong posture as `questionRelevant` elsewhere in this file, since a wrong page's diagram shown as if it were this question's is worse than none.

Only pages a chunk actually matched to are uploaded (`uploadPageImages()`), not every rendered page in a batch — a source with no diagram-bearing questions costs nothing here.

**Image filenames must use the document-global page number.** `matchingPageIndices()` returns indices *within the batch* (0–5). The first version wrote them straight into the filename, so every batch of a file wrote `page-0001.png`, `page-0002.png`, … and `upsert: true` let each later batch overwrite the earlier ones — every earlier chunk kept a pointer that now showed some other batch's page. Nothing errored; it was found only by downloading a stored image and looking at it (a Trial Johor Tangkak conductivity question pointed at a nanotechnology page 114 pages away). `uploadPageImages()` now takes a `batchOffset`, and `runIngestion()` takes `firstPageNumber` so a `--start-page` resume is numbered from the real page too. **Verify this feature by viewing stored images against their chunks, not by counting non-null pointers** — the broken version had excellent coverage numbers. Teacher-material chunks backfilled before the fix were repaired in place by `src/scripts/repair-teacher-page-images.ts` (re-OCR, re-match each existing chunk window by window, accept only a match in exactly one window, update `source_page_images` only — no rows deleted, nothing re-chunked; old pointers backed up to `.cache/backups/`). `chat-handler.ts`'s `resolveExamPageImages()` downloads at most `MAX_EXAM_PAGE_IMAGES` (2) per turn, scoped to `content_type = "past_year_question"` only — the exact population the measurement above covers — and appends them to the same `images` array a student's own attachment goes through, with a prompt note (`examImageNote`) telling the model these came from the knowledge base, not the student, so it doesn't credit or blame the student for a file they never sent.

**Downloading the page for the model to read is not the same as showing it to the student — that gap shipped as its own bug.** Reported: the tutor was answering diagram-dependent past-year questions by redrawing its own sketch of the diagram via the visual-generation tool (below), which is exactly the "approximation instead of the real picture" failure this feature exists to prevent — the model could *see* the real page, but the student never got a copy of it, only the tutor's text and, often, a machine-drawn recreation. Fixed by having `resolveExamPageImages()` return the same downloaded bytes twice: `anthropicParts` for the model's vision input (unchanged), and `dataUrls` — the identical PNGs base64-encoded — returned to the client as `examPageImages` on the chat response and rendered inline under the reply (`ChatMessageItem.tsx`), the same "not persisted with the message" posture as `visual`/`materials`. A data URL was chosen over a signed storage link because these render immediately, with no click, for as long as the message is on screen — the 5-minute-expiry problem that makes `materials`' download link mint-on-click doesn't apply to something meant to be visible from the moment the answer finishes. The visual-generation call (`ANTHROPIC_VISUAL_TOOLS`) is now skipped outright whenever `examPageImages.dataUrls` is non-empty: once the real page is going to be shown, a redrawn one is never an improvement, only a second, less accurate copy competing for the student's attention.

Coverage by subject: Sejarah past-year chunks have **no** page images (none needs one). Physics, Add Maths and Mathematics got them afterwards (2026-10-14; 428/430, 452/452, 398/398) from `src/scripts/backfill-past-year-page-images.ts`, which matches each stored chunk to its page against the ingest script's own OCR cache (exam label + exact text, or for model-chunked Mathematics a word run found on exactly one page), with no model calls, and also attaches the next page to a question printed last on its page (its diagram is often overleaf); extend its `SOURCES` table to add a subject. Chemistry has them for teacher uploads and for the textbook/past-year files in `~/Desktop/knowledge bases/chemistry/`, which were re-ingested with `--vision` on 2026-09-30/10-01: Buku Selekoh Akhir SPM 2024, Chemistry Form 5 KSSM, Kimia Tingkatan 5 KSSM, DLP Textbook Chemistry Form 4, Textbook Kimia Form 4 (BM) — 1,727 chunks, 1,538 with images. That re-ingestion replaced an older 1,955-row batch with no `source_file`, which turned out to span several of those files rather than one; it was deleted without a full backup and is not recoverable. Before deleting by a NULL-signature filter, confirm what it actually covers. The Buku Selekoh book's own answer scheme is distributed separately (QR / bit.ly link with a passcode on its last page), so most of its MCQs are dropped as `not_in_source`.

**This is forward-only.** It wires into the generic `ingest.ts` path and the teacher-upload path (`materials.ts`), both of which already render page images via `--vision`/always-vision respectively — any source ingested from here on gets this automatically. The ~2500 already-flagged existing past-year chunks are NOT backfilled: there is no stored page-number-per-chunk for historical rows to match against, and the subject-specific past-year scripts (`ingest-past-year.ts`, `ingest-physics-past-year.ts`) have their own bespoke OCR/insert pipelines that don't go through `runIngestion()` at all, so they need their own wiring as a separate follow-up, not covered here.

**When a diagram is shown (2026-10-14).** Page images now exist for every subject's past-year questions, which exposed three gaps in *when* `resolveExamPageImages()` shows one, all found in real chats. (1) A request for a **set** of past-year questions ("give me past year physics questions", "venn diagram past year") got none: the locator's single-question rule correctly refuses a general request, so the tutor listed diagram questions with no diagrams. A past-year request (`hasStrongPastYearIntent`) now runs `DIAGRAM_LIST_LOCATOR_PROMPT` with `DIAGRAM_LIST_LOCATOR_TOOL` (every box must name its excerpt, enforced by the schema after the model omitted it on 2/3 runs). Up to `MAX_LIST_DIAGRAM_REGIONS` (3) figures are checked in code: each must belong to its excerpt's own page, and a printed figure number must be one the excerpt's text refers to. The prompt note then tells the tutor which questions the diagrams belong to and in what order, so it presents those questions. (2) **Follow-ups that name no topic** ("where's the figure", "where is the diagram for each questions") are recognised by `FIGURE_FOLLOW_UP`. For past-year questions, the ones the previous reply presented are looked up from the reply itself (`pastYearQuestionsIn`), since they often came from the previous turn's exam lane and are not in this turn's retrieval. A question is kept only if the reply quotes two separate six-word runs of it (`presentedIn`): one run matched by chance in a textbook explanation. This is attempted only when the reply cites an exam (`CITES_EXAM`). For textbook figures, candidates come from the previous message's topic, plus a figure number the previous reply named. (3) Past-year candidates no longer **block** the textbook figure. Once Physics past-year rows had images, "show me how a transformer works" always had some, and the textbook path never ran. The past-year attempt now goes first and the textbook figure is tried when it shows nothing. `cropRegion()` also rejects strips over 6:1, which are a line of text, not a figure. Replayed on the real conversations: 35/36 across four runs, with 0 images on all negatives ("how does a transformer work", "what is ohm's law", "where is the mistake in my working"). The one miss is locator run-to-run variance on a list request. **Exam questions stored as worked examples (2026-10-16).** Teachers' notes store a trial question with its worked solution as `worked_example` under an exam label ("TRIAL N. SEMBILAN 2023 – Q03"); 99 such rows have a diagram and a page image and were never considered, so the tutor presented N. Sembilan 2023 Q3 with its Diagram 3 described in words. `isExamQuestion()` now admits them, but only on an exam turn (past-year request, named exam, pasted figure reference, figure request or follow-up): the gated teacher lane puts them first for any question on their topic, and without the gate 9/9 fresh-chat topic questions ("what is the meaning of standard solution") showed the diagram. After: 0/9 on those, 3/3 on "give me one past year question on chemistry". Still open: the exam lane (`match_past_year_by_exam`) only returns `past_year_question` rows, so naming the paper ("trial negeri sembilan 2023 chemistry question 3") cannot reach a question stored as a worked example; that needs the exam-label columns backfilled for those rows and the RPC widened. Two more follow-up misses the same day, both fixed: "wheres the diagram" (no apostrophe) didn't match, and "can you just give me the file for it" wasn't a follow-up at all, so a topicless turn's own retrieval offered a Chemistry "Rajah 10" and the locator showed it in a Physics conversation about Diagram 10. Now a follow-up after a reply that cited an exam only ever gets the questions the last **two** replies presented (the one before may have been "I can't show it"), never this turn's retrieval, and the locator is shown the start of the previous reply so "the first question" and "it" resolve. Replayed 3x: Kelantan 2023 Diagram 10 on all 6 follow-ups. **No diagram when the tutor is asking for the subject (2026-10-19).** A past-year request with no subject in the message or the conversation ("do you have any past year docs?") sets `pastYearSubjectUnknown`, and the tutor asks which subject — but the `exam_images` node still ran and showed whichever past-year diagram retrieval ranked first (Trial Pahang 2022 Q3, 3/3 replays), which also lit up the follow-up buttons under a reply that had presented no question. The node now returns nothing on that turn.

### Not citing sources for off-topic chat (`isOffTopicChat`, `isSmallTalk` in `small-talk.ts`)

Reported twice: a plain "hi" showed a "Sources (n)" toggle, and later, longer small talk ("what's your favorite movie", "tell me a joke") did too. `match_content_chunks` has **no relevance floor at all** — it always returns its nearest `match_count` chunks, "nearest" being relative with nothing under it — and `sources` used to echo that list straight into the response regardless of whether the reply taught from any of it.

**A cosine-similarity floor cannot fix this**, and was measured before being ruled out: off-topic chat like "how old are you" scored 0.831 against the real KB, *above* genuine Sejarah questions like "explain the causes of the Malayan Union" (0.816) and "sebutkan faktor kejatuhan kerajaan melaka" (0.821). That is the identical overlapping-distributions problem already documented for `TEACHER_MATERIAL_MIN_SIMILARITY` — a closed-vocabulary Malaysian curriculum's short, common phrasing sits in the same similarity band as ordinary conversation, for the same reason a single number couldn't separate teacher-material relevance either.

So this is a classification, not a number, and it costs a model call — `isOffTopicChat()` is a forced tool call (`report_topicality`, one boolean field) on `TUTOR_MODEL`, same pattern as `judgeTeacherMaterialRelevance()`. `isSmallTalk()` runs first as a free short-circuit (an all-words-in-a-closed-greeting-set check, no model call) so the common case — a bare greeting — costs nothing; the classifier only runs for longer off-topic messages that word-matching can't recognise. It fails **open** (treats the message as academic, so sources still show) on any error or empty tool call, the opposite failure direction from the teacher-material judge: a wrongly-hidden sources list costs a convenience, but a broken classifier should never look like a new bug by hiding sources on real schoolwork questions. Measured: `max_tokens: 32` hit `max_tokens` before the single field finished emitting on every one of 9 test messages (empty `tool_use.input`, which reads as "fails open" harmlessly, but for the wrong reason) — `64` completed all 9 correctly.

This only gates whether `sources`/`materials` are shown in the response. Retrieval, the context block, and the model call are all untouched — the tutor still sees whatever the (deliberately ungated) whole-KB lanes returned, same as before this existed, and the system prompt's own scope rules are what actually make it decline to answer.

### Choosing an LLM (`src/lib/providers.ts`)

A user can pick which model answers: **Claude** (Anthropic), **GPT** (OpenAI) or **IlmuChat**. The choice is stored per conversation (`conversations.provider`, `sql/migrate_add_conversation_provider.sql`) so the same person can compare providers on the same question, and a reloaded conversation answers the way it has been answering. Null means `DEFAULT_PROVIDER` (Anthropic — the one path whose scope compliance, vision handling and cost are all measured).

**Only the main tutoring answer follows the choice.** `judgeTeacherMaterialRelevance()` and the visual-diagram decision stay on Anthropic. Both are forced tool calls with Anthropic-format schemas, and the gate is written to fail **closed** — routing it through a provider whose forced-tool-call behaviour hasn't been verified would degrade teacher-material retrieval on every request, silently, in a way no student could see. Porting them is a separate job with its own verification, not a config flag.

**Model ids are read off the account, never guessed.** `OPENAI_TUTOR_MODEL` defaults to `gpt-5.6-terra`, resolved by matching "terra" against a live `models.list()` on the deployment's own key — it was the only match out of 132. `src/scripts/list-ilmuchat-models.ts` does the same for any OpenAI-compatible endpoint (`--provider openai` to check the OpenAI side). This matters because "use the highest-end model" isn't answerable from outside: `/v1/models` returns an unordered set of ids with no tier or capability field, so which is "highest" is a judgment about that vendor's lineup, and a guessed id produces a config that looks correct and 404s on the first student question. Note `gpt-5.6-terra` is a reasoning model and its reasoning tokens come out of `max_completion_tokens` — measured at 349 on a full Add Maths turning-point question against the 4096 cap, so the visible answer budget is smaller than the cap implies. It completed comfortably there; re-measure before assuming longer worked solutions fit.

IlmuChat is OpenAI-compatible, so `kind` is `"openai-compatible"` rather than `"openai"`: the branch is about wire format, not vendor, and one client covers both. Attachments are converted at that boundary — `attachments.ts` keeps emitting Anthropic image blocks as the single definition of what an attachment *is*, and the chat-completions path rewrites them to `data:` URLs. IlmuChat needs all three of `ILMUCHAT_BASE_URL`/`_API_KEY`/`_MODEL` before it appears at all; a partial config would fail at call time with a confusing 401.

`KNOWN_MODEL_PRICING` in `providers.ts` carries published **standard-tier** per-1M rates for models actually checked — `claude-sonnet-5` 2/0.2/10, `gpt-5.6-terra` 2/0.2/12, plus sol/luna/astra — so a known model is safe for students with no env configuration. Batch, Flex and Fast are priced differently and unused here; Terra also has a long-context tier (over 272K input it moves to $4/$18) which these numbers ignore, since a turn is a ~2.3k prompt plus at most 12 chunks. An env override always wins, which is how a rate change is corrected without a deploy and how an unlisted model becomes student-usable at all.

**Pricing is a safety gate, not a nicety.** `costUsd()` is keyed by model string and returns **0** for a model it has no rate for; a 0 cost never moves `usage_daily`, so the student daily cap never fires — an unpriced provider open to students is an uncapped spend path that looks exactly like a working one. (This is not hypothetical: the Haiku→Sonnet switch hit it when `TUTOR_MODEL` changed and the pricing key didn't.) So `PRICING_PER_1M_TOKENS` is now *generated* from the provider registry rather than maintained separately, and a provider with no configured rates is offered to **teachers only** — they're exempt from the cap regardless, so nothing is lost and the restriction lifts by setting two env vars. Measured: an OpenAI turn recorded a cost delta of only the Anthropic gate + visual call, with the answer itself contributing $0.

**A present-but-empty env var is treated as absent** (`blankIsAbsent()` in `src/lib/env.ts`), because `.env.example` ships every optional key blank and copying it is the documented first step. Zod does not do this for free and fails two different ways. On a string var `""` fails `.min(1)`/`.url()` and `.optional()` does not rescue it — optional admits `undefined`, not empty — so the process refuses to boot over a variable the operator deliberately left unset. On a price var the failure is silent and far worse: `z.coerce.number()` parses `""` as **0** (`Number("") === 0`), which is a *defined* rate of zero rather than a missing one, so `providers.ts` counts the provider as priced, offers it to students, and every turn records $0 against the daily cap. A blank line in `.env` therefore becomes an uncapped spend path that looks exactly like a working configuration — the same hazard the pricing gate exists to prevent, arriving through the one file everybody copies. Empty values are trimmed before the check, since a trailing space after `=` is invisible in an editor.

`resolveProvider()` falls back rather than erroring — a conversation can name a provider that was later unconfigured, and a student can inherit a teacher-only choice — and the response reports which provider **actually** answered, so the picker is corrected from what ran rather than from what was asked for. The column is treated as optional at runtime: deploying this code before running the migration logs a warning and degrades to the default provider instead of failing every turn. Both halves need guarding, and only the write half is obvious. PostgREST rejects the **whole request** with `42703` when a selected column is missing rather than returning a row without it, so an unguarded `select("id, provider")` on the conversation lookup is not a lost preference — it is a 500 on every turn that carries a `conversationId`, which is every turn after the first message. The result reads as a total chat outage, while the write-side failure it was paired with reads as a warning in the log. The lookup retries without the column and caches the answer in `providerColumnPresent`, so the un-migrated state costs one failed round trip per process rather than one per request.

### Cross-language retrieval (`src/lib/query-glossary.ts`)

**The knowledge base is language-partitioned by subject**, and that makes a Malay question unable to reach half of it. Add Maths, Mathematics and Physics were ingested from English textbooks; most Chemistry teacher material and all of Sejarah is Malay. `multilingual-e5` is cross-lingual in principle, but measured on the real KB same-language text wins cosine search decisively:

| query | expected | Malay hits | English hits |
|---|---|---|---|
| `pembezaan` | Add Maths | 0/6 | 6/6 |
| `kamiran` | Add Maths | 2/6 | 6/6 |
| `hukum linear` | Add Maths | 2/6 | 6/6 |
| `keelektrikan` | Physics | 0/6 | 6/6 |

It does not merely miss. `pembezaan` returns six **Chemistry** chunks, because a Malay query gravitates to the Malay-heavy part of the corpus. Strict grounding then makes the tutor refuse a question it holds 116 chunks on — reported as *"Terangkan cara membezakan fungsi dalam Add Maths langkah demi langkah"* answered *"Saya belum ada nota yang menerangkan kaedah pembezaan"*. **This failure mode is invisible as a wrong answer**; it surfaces only as a tutor that seems oddly useless in Malay, which for a Malaysian student body is most of the traffic. The successes are the tell: `logaritma`, `janjang`, `tekanan`, `daya dan gerakan` all score 6/6 because they are cognates or appear verbatim; the failures are Malay words with no surface anchor in English text.

`rewriteMalayTerms()` rewrites known SPM terms to the English wording **the corpus actually uses** — values taken from the `topic` column, not a dictionary, since the point is to land on text that exists — and `chat-handler.ts` runs the result as a sixth retrieval lane beside the original. Measured over 13 queries: **6 improved, 0 worse, 7 unchanged**. It never regresses, for three structural reasons: the rewrite returns `null` when it recognises nothing (so an English question pays no embedding and no query), the rewritten query runs *beside* the original rather than replacing it (so a bad rewrite costs nothing), and its hits are merged **last** (so they only fill slots the original-language lanes left empty). That ordering is what lets the lane be added without re-tuning any cutoff above it.

Substitution, not appending: `"pembezaan differentiation"` measured worse than `"differentiation"`, because the Malay tokens are precisely what pulls the vector toward the Malay-heavy corpus. A useful second-order effect is bilingual coverage rather than mere translation — `"bagaimana nak kira tekanan"` returns Malay Physics chunks from the original query *and* English ones from the rewrite, and neither query reaches both halves alone.

**The alternative was rejected on cost, not merit.** The thorough fix is a bilingual anchor in `passageTextForChunk()` plus a full re-embed, giving every English chunk a Malay handle. That rewrites what all ~10.7k chunks embed and therefore moves **every similarity score in the system**, invalidating `TEACHER_MATERIAL_MIN_SIMILARITY` (0.75), the 0.83 judge fallback and the lexical IDF floor — all empirically tuned, and at least one already known to have drifted. Do not attempt it without a probe harness able to re-measure all of them. The glossary is the reversible half: query-side only, no model call, one extra local embedding.

The glossary is deliberately **not a translator**. It covers topic vocabulary and the instruction verbs that open a Malay exam question — a closed set that can be checked by eye. An unknown word is left alone, which degrades to today's behaviour rather than to a wrong rewrite.

### Guide, don't tell (students only, 2026-10-20)

`TUTOR_SYSTEM_PROMPT`'s GUIDE, DON'T TELL block makes the tutor coach a **student** to the answer of anything they are meant to answer themselves (calculations, homework, past-year questions) instead of handing it over; the asker line before the question repeats it every turn. Concepts, definitions and methods ("what is an acid", "how do I find the turning point") are still taught in full, and a **teacher** gets full answers and marking schemes immediately. A past-year question goes to a student without its scheme. The full worked solution comes once the student has made a real attempt (an answer that fits the question; "B" to a written question does not count) and is still stuck, or after about three hints; each hint must give away more than the last. Two things only worked once written as explicit triggers: hints that re-word themselves (a stuck student got the same "what is a?" four times) and a solution that never arrives — "if your last two or more replies were hints on this question and they are still stuck or ask to be shown, the full solution is THIS reply" fixed both, in the system prompt and in the asker line. Measured on scripted conversations: a first-turn "just give me the answer" gets a hint, a correct attempt gets confirmed with the working, a wrong one gets its wrong term pointed at without the fix, and "please show me" after hints gets the solution (2/2 runs). This is prompt behaviour, not enforced in code: the model sometimes front-loads most of the working into an early hint while still leaving the last step to the student. **Scoped (2026-10-23):** measured on golden-v5 through the full pipeline, the rule over-applied. 33 of 107 answerable items were coached instead of answered, 25 of them plain facts or explanations ("apakah mangkin penghidratan etena", resistivity of copper), costing 0.201 correctness. The exemption for concepts sat at the end of the block, while the per-turn STUDENT line said "guide them to answers rather than giving them" with no exception, and the model followed the line. Both now open with the split: answer anything the student asks to know or understand, and coach only what they are meant to work out. Paired rerun: correctness 0.643→0.752, faithfulness 0.854→0.904, and calculations are still coached.

### Reply consistency (`src/lib/reply-language.ts`)

"The answers aren't consistent" was measured before anything was changed, by running identical questions through the real `handleChatRequest()` repeatedly. **Retrieval is deterministic** (identical chunks on 5/5 runs for every question) and **the relevance judge is stable** (the same verdict 5/5), so the variation is all downstream of retrieval. In 27 runs across three providers every answer contained the expected content; wording and length vary (Claude 1.7k–2.6k characters on the same question), which is ordinary sampling and not something to engineer away. **Sonnet 5 rejects non-default `temperature`**, so the usual "set temperature to 0" fix is not available here: it would return a 400 on every turn.

What *was* a real failure is **reply language, and it is provider-specific**. Over 12 identical turns each: Claude 0/12 wrong, GPT 0/12, **IlmuChat 3/12**. Those three were one reply that opened in Malay and continued in Traditional Chinese, and two that opened in English and switched to Malay from the first step heading. All three answered *English* questions, so the model's inferred language lost to the pull of Malay teacher material in the context. `studentLanguage()` now decides the language in code and `replyLanguageDirective()` states it on every turn beside the asker line, the same way the asker's role is stated rather than inferred. It returns `null` on an ambiguous question, which adds no directive and leaves the prompt's own history-aware rule in charge, so an unclear question is never forced into the wrong language. Explicit switch requests are checked before word counting, because "in malay" counts as English by vocabulary. After the change IlmuChat was 0/12.

A reply containing CJK script is discarded (`containsCjk()`): one retry on the same provider, then the default provider answers, and the response's `provider` reports who actually wrote it. CJK is never a valid reply language here, so code can act on it; Malay/English mixing is *not* policed after the fact, because formulas and quoted source terms make any heuristic unsafe to act on. That is why the directive is the preventive half. Every attempt is billed through `recordUsage()`, including a discarded one.

The no-meta rule in `TUTOR_SYSTEM_PROMPT` now also covers **the instructions themselves** and the notes placed before the question. Claude had opened a reply with *"Saya perhatikan bahawa arahan sistem menyatakan saya sedang bercakap dengan guru"* ("I notice the system instructions say I'm talking to a teacher"). The rule's examples only covered retrieval ("the database", "sources").

**Test on a student account to see what students see.** The asker line changes the prompt's behaviour: a teacher is told when their material has a gap or error and needs amending ("I want to flag a gap in it"), while a student is pointed to their teacher. Answers read quite differently between the two roles on the same question, by design.

### Turn routing (`src/lib/router.ts`, LangGraph)

Before retrieval, `routeTurn()` classifies the message with a two-node LangGraph `StateGraph`: a free `rules` node, then a `classify` node (forced tool call `route_message` on `TUTOR_MODEL`) only when no rule decided. Routes: `schoolwork`, `small_talk`, `off_topic`, `app_help`. The last three are "conversational": `handleChatRequestUntraced` skips embeddings, all retrieval lanes, the judge, the diagram locator and the visual-decision call, and adds `routeNote()` to the prompt so the strictly grounded tutor doesn't answer "hi" with "I have no notes". This replaces the post-hoc `isOffTopicChat()`, which only hid Sources after the full pipeline had run.

**Every undecided or failed path resolves to `schoolwork`.** Calling schoolwork "conversation" is the costly error (a real question answered with no material); the reverse wastes one retrieval. Rules run in a fixed order: no text / attachment / confirmation of an offer / strong past-year intent → schoolwork, then closed-set greeting → small_talk. File requests are not a rule any more (no keywords): `detectFileRequest()` decides them in the same node, and a file request overrides a conversational route. The confirmation rule must stay ahead of `isSmallTalk`, because "yes" is in the small-talk word set — before routing, a "yes" to an offered PDF was treated as off-topic and its card was suppressed. Exam filters inferred from history also veto the conversational route in the handler. The router shows up in Langfuse as `router` (+ `router-classifier` generation when the model ran).

### Follow-ups rewritten to stand alone (`src/lib/standalone-question.ts`)

The tutor's answer call gets the last 20 messages, but every step before it saw only fragments: retrieval prepends 300 characters of the last message, the router 300 of the last reply, the diagram locator the previous user message. That breaks as soon as the last message has no topic of its own. Reported 2026-10-14: "show me the transformer" → a Kelantan 2023 Diagram 10 question → "wheres the diagram" → "I can't show it" → "can you just give me the file for it", which was searched with nothing about transformers or Physics in reach; retrieval returned a Chemistry "Rajah 10" and the locator showed it.

`standaloneQuestion()` (forced tool call `report_standalone_question`, Langfuse generation `standalone-question`) reads the last 6 messages and rewrites the new one so it makes sense alone, e.g. "can you just give me the file for it" → "…the diagram file for Diagram 10 in Kelantan 2023 Physics Question 10 (simple transformer)". It runs in the `route` node **beside** the router, so it adds little wall-clock time (measured 1.4–4.5 s, router ~2 s); it is skipped on a first message and a closed-set greeting, and returns null when the rewrite equals the message or the call fails, which is exactly the behaviour before it existed. Where it is used:

- **Retrieval:** a seventh whole-KB lane on the rewrite, merged **ahead of** the prior-turn lane (on kb_chunks that lane alone fills the block, so a lane merged after it never contributes), and the past-year lane searches the rewrite instead of the bare message. The teacher lanes, the relevance judge, the file-attachment gate and the subject guard on teacher material are untouched — they were tuned on the bare question and their failure modes are documented above.
- **Diagrams:** the locator is told what the student means; textbook follow-up candidates are searched on the rewrite; and when the rewrite names exactly one subject, other subjects' figures are dropped in code. That guard may use the conversation (unlike the teacher-material one) because here a missing diagram is the cheap error and a wrong one is the bug.
- **The answer itself still gets the student's verbatim words** and full history.

Replayed old vs new on 25 follow-ups from 5 real conversations: context blocks moved on-topic on the topicless follow-ups ("okay can i see that" went from 6 Chemistry/Physics-mixed pages to Physics refraction pages plus the concave-lens past-year question, whose diagram is now shown); the transformer conversation's follow-ups show Kelantan 2023 Diagram 10; "what about transformer in ai" no longer shows a Physics diagram; "give me the past year style" no longer shows Mathematics price-index tables in a transformer conversation. A rewrite can attach the wrong topic — "show me the NONA method" (a Chemistry mnemonic) was rewritten as Physics refraction, the previous topic — which is why it is an extra lane and never replaces the student's own query: that turn still led with the teacher's Magic Triangle notes. The replay also exposed an older bug: a locator answer naming several figures ("4.32, 4.33") was compared as the digits "4.324.33" and every box was dropped; it is now read as a list.

### The turn as a graph (`src/lib/chat-graph.ts`)

After the setup in `handleChatRequestUntraced` (auth, usage cap, conversation, history), one turn runs as a LangGraph `StateGraph`: `route` → `retrieve` → `exam_images` / `materials` / `resources` (parallel) → `compose` → `provider` → `generate` → `persist` → `visual`. `chat-graph.ts` owns only the topology and state; the steps are the stage functions in `chat-handler.ts` (`retrieveContext`, `resolveExamImagesStage`, `resolveMaterialsStage`, `buildResourceNote`, `chooseProvider`, `generateAnswer`, `persistAnswer`, `decideVisual`), passed in as `ChatNodes` so there is no runtime import cycle. `npm run router:graph` prints the Mermaid diagram. A node cannot share a name with a state channel, hence `routeDecision` / `materialsResult` / `visualResult`. A conversational route skips `retrieve` and everything reading it, but still runs `resources` (the link catalogue has always been in the prompt). Retrieval failing ends the graph and the handler returns the same 500.

Each node is one Langfuse `chain` observation made active while it runs, so a step's own spans (embeddings, lanes, model calls) nest inside it; it carries `langgraph_node` / `langgraph_step` metadata and an output that records only key → size, never chunk text or base64. The LangChain callback handler was tried and dropped: it recorded the nodes but left them as siblings of the steps' own spans, plus `LangGraph` / `RunnableLambda` / `__start__` noise. `tracing.ts` also masks base64 media on every exported span as a last line of defence.

**Checked by comparing the exact prompt the tutor receives**, old code vs new, with the paid answer call stubbed (the judge and locator still run): 19–20 of 22 identical per stage, and every difference was in the retrieved chunks on a question the teacher-relevance judge answers differently run to run (the old code disagrees with itself on those). Do that comparison again after any restructure.

### "What do you have" questions (`src/lib/catalogue.ts`, route `catalogue`)

A question about what the tutor holds — "do you have any add maths resources", "how many chemistry topics are there", "apa topik fizik yang ada", or a follow-up "how many are there?" — is routed `catalogue`. It skips retrieval like the other conversational routes, and the graph's `catalogue` node adds a WHAT YOU HAVE block: every subject, its topics, its past-year question total and its teacher-file count, read from `content_chunks`/`materials` and cached per process for 10 minutes. Retrieval cannot answer these: the question has no topic to search on, the lanes return a mixed handful, and the tutor counted what it saw. Found in the first annotation round — it told a teacher there were "six" Add Maths topics including "Limits" (there are 18; Limits is not an SPM chapter).

**Add Maths, Chemistry, Mathematics and Physics are listed by form (2026-10-22).** Topics are filed by name only, so "what's in Form 5 Add Maths" had nothing to answer from. `FORM_CHAPTERS` in `catalogue.ts` maps each form's printed chapter numbers to the topic column's own names, taken from the chapter headings in each subject's Selekoh 2026 modules. It is keyed by number, not position, because SPM Mathematics also examines nine Form 1–3 chapters (F1C6 Linear Equations … F3C9 Straight Lines), so the numbers have gaps. Chemistry Form 5 Chapter 5 is filed as "Chemical Consumer" (printed as Consumer and Industrial Chemistry). Mathematics Form 5 Chapter 8 (Mathematical Modeling), Physics Form 4 Chapter 1 (Measurement) and Chemistry Form 4 Chapter 1 (Introduction to Chemistry) are not in their modules; they come from the KSSM textbooks. Chemistry Chapter 1 was filed under the catch-all topic "General", which the catalogue hides, so the list said it had no material; golden-v5 caught it. Its 42 rows were re-filed as "Introduction to Chemistry" on 2026-10-26 (DLP Form 4 pp.12–31 plus 5 unpaged rows, and 7 rows of the Malay textbook's Bab 1; the preface, glossary and index stay "General"). No re-embed was needed, because the topic is not part of a textbook row's embedded text. The Form 1–3 chapters were also added to `SUBJECT SCOPE`, with a note that Form 2 Coordinates and Form 3 Straight Lines are core Mathematics: the block calls Coordinate Geometry Add Maths only, which a Form 2 question would otherwise trip. Other subjects stay unsplit, and the tutor is told not to assign a form to them. What is *inside* one chapter ("what subtopics are in integration") is routed `schoolwork`, not `catalogue`: the answer is the module's chapter cover pages, which were tagged "SPM Additional Mathematics Form N, Chapter k" and re-embedded so they carry their form. Measured: router 22/22 on subtopic vs catalogue questions; "is linear law form 4 or form 5?" → Form 4, Chapter 6.

**Sejarah lists its chapters under each form (2026-10-22).** Sejarah is filed by form, so its topics are "Form 4" / "Form 5" and no row names a chapter. `CHAPTERS_OF_FORM` holds the ten Bab names per form, as printed in the Selekoh 2026 Sejarah modules, which cover every chapter. **A count question is catalogue even when it names past years.** "how many past year questions do you have for sejarah?" was answered "10": the router's past-year rule sent it to schoolwork, and the subject-only exam filter it parses to also vetoed a catalogue route in the handler, so the tutor counted what retrieval returned (Sejarah holds 1641). The rule now skips messages asking "how many"/"berapa"/"bilangan"/"jumlah" and leaves them to the classifier (18/18 on counts vs. past-year look-alikes, such as "how many marks is this question worth"). A catalogue route also wins over an exam filter that names only a subject; a named paper still keeps the exam lane and its coverage reply. The count line reads "past-year and trial (percubaan) exam questions": labelled "past-year" only, "berapa soalan percubaan kimia" was told there were no trial questions.

Format matters with the weaker provider: on one line, "18 topics | 452 past-year questions" was read by IlmuChat as 452 *per topic*, so each total sits on its own line labelled "all topics combined"; topics are separated by semicolons because names contain commas ("Acid, Base and Salt"). The block is headed WHAT YOU HAVE rather than CATALOGUE because a leaked heading ("based on the catalogue…") reads as machinery. Measured after the change: correct counts on 9/9 turns across IlmuChat and Claude. A file request ("ada nota add maths tak") still goes to `schoolwork` by rule, since it may attach a PDF.

### Tracing (`src/lib/tracing.ts`, Langfuse)

Every chat turn is one Langfuse trace (`chat-turn`), with the user as `userId` and the conversation as the session. Inside it: `embed-queries`, `retrieval-lanes` (what each lane returned, by id/source/score, no chunk text), a `context-block` event (the exact 12 chunks the tutor got, and which teacher gate each passed), and a **generation** for every model call — `teacher-relevance-judge`, `off-topic-classifier`, `diagram-locator`, `standalone-question`, `material-topic`, `visual-decision`, `tutor-answer` (all three providers) — with model, tokens and latency. Each generation's cost comes from `usage.ts`'s own pricing table (injected via `setTracingCostFn`), so Langfuse shows exactly what the student cap is charged, IlmuChat included; an unpriced model shows no cost rather than $0. A failed call is a generation with level `ERROR`, which is how a fail-closed fallback becomes visible: the judge falling back to 0.83 otherwise looks like a normal turn.

Off unless `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` are both set (`LANGFUSE_BASE_URL` defaults to EU cloud). With no tracer provider registered the OTel API hands out no-op spans, so tracing can never break a turn. It initialises on first import of `tracing.ts`, so the Fastify server, the Vite plugin and scripts all get it without wiring; a script ending in `process.exit()` must `await flushTracing()` first or batched spans are dropped. New Anthropic calls should use `tracedMessage(name, params)` instead of `anthropic.messages.create`, which is a drop-in replacement.

**Images never leave the process.** `redactMedia()` replaces base64 image/document blocks and `data:` URLs before anything is recorded, and the processor's own media upload is off as a second guard. Students' questions and the tutor's answers *are* exported to Langfuse, and the users are school students — use a region/self-hosted instance that fits that, and don't add attachment bytes to a trace.

### Embeddings (`src/lib/embeddings.ts`)

Both embedding call sites (ingestion and query-time embedding in `chat-handler.ts`) go through `src/lib/embeddings.ts`, which runs `multilingual-e5-base` (768 dims, int8-quantized) locally in-process via `@huggingface/transformers`/`onnxruntime-node` — free, no per-token cost, which matters since query-time embedding runs on every student question. Chosen over `gte-base` because source documents can be multilingual (e.g. Malay-language textbook material), which it's explicitly trained for.

**Important:** E5 models require an asymmetric `"query: "` / `"passage: "` text prefix — skipping this causes real retrieval degradation. `embeddings.ts` exposes `embedQuery()` (student questions) and `embedPassage()` (knowledge base chunks in `ingest.ts` and `src/scripts/reembed.ts`) — there is no bare `embed()`; using the wrong one silently works but retrieves worse.

This runs in-process rather than as a Supabase Edge Function — that was tried first (for `gte-base`) and abandoned after repeated runtime failures, consistent with community reports that Supabase Edge Functions' resource sandbox only reliably supports smaller (~384-dim) models like `gte-small`. Since both call sites already run as plain Node processes, there's no serverless constraint to design around — the model loads once per process via a lazy singleton and stays warm.

Note: `package.json` pins `onnxruntime-node` to `1.23.0` via `overrides` — `@huggingface/transformers`'s default (`1.24.3`+) dropped prebuilt Intel Mac (`darwin-x64`) binaries.

### Database (`sql/schema.sql`)

Postgres with `pgvector`. Key objects:
- `kb_chunks` — what production retrieval reads since 2026-10-13 (`RETRIEVAL_BACKEND=kb_chunks`). `origin`: `textbook` (16 rebuilt textbooks), `carried_teacher`, `carried_past_year`, and `carried_revision` (the revision books' notes and worked solutions — 445 rows the cutover missed, since it carried only teacher and past-year rows; `sql/migrate_carry_revision_chunks.sql`). Carried rows keep their `content_chunks` vector and point back via `legacy_chunk_id`; a trigger (`sql/migrate_sync_kb_chunks.sql`) keeps them in step, because every ingestion path still writes to `content_chunks`. Do not drop `content_chunks` while that is true.
- `content_chunks` — the knowledge base, `embedding vector(768)` (multilingual-e5-base) with an HNSW cosine index. `source_file` records the originating PDF's basename (`sql/migrate_add_chunk_source_file.sql`), set by `runIngestion()` from both entry points. It exists because nothing previously pointed a chunk back at a file — `source` is an LLM-authored note like "Example 4", and `material_id` covers only teacher-portal uploads — which made "is this PDF already ingested?" unanswerable by lookup. An audit of a 186-file folder had to fall back on content matching, and cosine similarity, exact phrase search and indexed phrase search all failed calibration against files of known status; vision-OCR'd content defeats text matching outright, since the stored text is the transcription and never the source's own wording. Rows predating the column are `NULL` and cannot be attributed **by content**. They can sometimes be attributed by **provenance**, which is a different thing and is what `src/scripts/backfill-past-year-source-file.ts` does: each pre-migration past-year batch was one run of one script, and those scripts hardcode their input path, so the file is known from the code rather than guessed from the data. That recovered 882 rows (Add Maths 452, Physics 410 + 20 weekly-quiz). Sejarah's 5 are deliberately left `NULL` — labelled with a section heading that places them in no file. (Chemistry's old NULL batch from 6 Aug has since been replaced by attributed re-ingestions; see the diagram section above.) Two traps that cost a run each: `NOT ILIKE` does not match `NULL` (21 Physics rows with no `source` are book rows, since the quiz branch always writes a literal label and can never emit null), and rules sharing a population must all be counted **before** any of them writes. Ingesting a single file is now safely repeatable: delete where `source_file = X`, re-run. Vectors from different embedding models/versions are never comparable — mixing them silently breaks retrieval with no error. Past migrations (kept for reference/pattern): `sql/migrate_gte_base*.sql` (OpenAI → gte-base), `sql/migrate_e5_base*.sql` (gte-base → multilingual-e5-base), both via the same add-column → `npm run reembed` → drop-old-column-and-rename dance.
- `users` / `conversations` / `messages` — per-user chat history; `users.telegram_id` and `users.email` are both nullable+unique, since one `auth_user_id` is meant to be shared across web and Telegram, with `messages.channel` tagging the origin for analytics only. `users.role` (`'student' | 'teacher'`, default `'student'`) gates material uploads and the usage cap.
- `materials` — one row per teacher upload (`src/lib/materials.ts`); `content_chunks.material_id` (nullable FK) attributes ingested chunks back to it. `status` (`'processing' | 'done' | 'failed'`) and `file_path` (private `materials` storage bucket, signed-URL download) track upload/ingestion state.
- `usage_daily` — one row per `(user_id, usage_date)`, incremented via the `increment_usage` RPC; backs the per-student daily spend cap in `src/lib/usage.ts`.
- `match_content_chunks(query_embedding, match_count)` — the whole-knowledge-base retrieval path; a pure nearest-neighbor cosine search across all of `content_chunks` (subject/topic pre-filtering was removed — chunk-level `subtopic` tagging plus the tutor's own judgment does the narrowing instead).
- `match_teacher_materials(query_embedding, match_count)` — same search restricted to `material_id IS NOT NULL`, and unlike the above it returns `similarity` so callers can gate on actual relevance rather than rank (`sql/migrate_add_teacher_material_lane.sql`).
- `match_teacher_materials_lexical(query_text, match_count, min_term_idf)` — keyword lane over teacher chunks, scoring the sum of per-term IDF over the whole KB and ignoring any term below `min_term_idf`. Backed by the `content_tsv` stored generated column (`to_tsvector('simple', content)`) plus two GIN indexes. `sql/migrate_add_teacher_material_lexical_lane.sql` documents why `ts_rank` and teacher-subset IDF were both built, measured, and rejected — read it before changing the scoring.

### Frontend (`frontend/src/`)

`App.tsx` is the top-level state container: session (via `useSession.ts`, wrapping Supabase Auth), profile/role (`lib/profileApi.ts`), the conversation list (`lib/conversationsApi.ts`), and the active conversation's messages — new conversations get a centered composer (`ChatInput` with `variant="centered"`) that switches to the docked bottom layout once the first message exists. There's no router — screens like `MaterialUpload.tsx` (teacher-only, gated on `profile.role === "teacher"`), `MaterialsLibrary.tsx`, and `ProfilePanel.tsx` are just conditionally rendered based on boolean state in `App.tsx`. Streaming responses go through `lib/chatSource.ts`. `ChatMessageList.tsx` auto-follows new content via a persistent `stickToBottomRef` (updated only by genuine user scroll events, not re-derived from scroll geometry on every render — that re-derivation approach breaks under batched/bursty streaming updates). `VisualRenderer.tsx` renders the diagrams from `src/lib/visual.ts`; `MarkdownContent.tsx` + KaTeX render math. **The app is dark-only** ("Night revision", 2026-10-16): `index.html` puts `class="dark"` on `<html>` and `index.css` pins Tailwind's `dark:` variant to that class, so every existing `x dark:y` pair resolves to its dark half regardless of the OS setting, and the tokens in `:root` are one dark set. The action colour `--color-brand` is a light green, so anything filled with it uses `text-[var(--color-on-brand)]`, never `text-white` (1.6:1). Past-year diagrams sit on a paper-coloured `.exam-paper` card headed by their source label (`examPageImageLabels` on the chat response, filled in `locateDiagrams()` only when one label is certain for the page). Layout: `TopBar` carries the wordmark, Materials / Links / How to use / Add material and New chat; the chat history `Sidebar` is a drawer at every width; `FilesPanel` lists every teacher file this conversation's answers listed (newest first, grouped by topic, so a new question adds to the list rather than replacing it) beside the chat at `xl` (collapsible to a strip showing the count; the choice is kept in `localStorage`), and below `xl` the top bar's Files (n) button opens the same list as `FilesDrawer`; the latest answer that presented a past-year question gets Check my answer / Give me a hint / Another like this (`quickActions`). Whether it did is decided by the server from the reply's own text (`presentsPastYearQuestion`: a diagram was shown, a retrieved past-year question is quoted per `presentedIn`, or the reply cites an exam and is shaped like a question per `ASKS_QUESTION`). Not from `sources`: the past-year lane puts 2+ such questions in nearly every context block (measured 21/21 turns), so the first version showed the buttons under almost every answer. Measured on 33 real replies: buttons on the 3 that gave exam questions, none on the other 30. `presentedIn` compares the reply against the question part only, cut at the answer (`ANSWER_START`: "Jawapan:", "Answer:", "Marking Scheme", "Penyelesaian"…): a reply teaching the four-keyword definition of an acid quoted Trial Kedah 2023 Q9(i)'s answer, which is that same definition, and showed the buttons under a reply that asked nothing (2026-10-19). Replayed on 45 real replies: that one turned off, and the 5 that presented a question kept them. Fonts: Space Grotesk / IBM Plex Sans / IBM Plex Mono.
